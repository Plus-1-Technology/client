What this proposal covers

Phase 1 · Submission Intake Automation

Phase 1 spans the path from inbound RFP email to a validated submission ready for Fusion. Rating, claims processing, and policy administration remain inside Fusion, where the existing actuarial tools and workflows continue to operate untouched. This proposal addresses the manual data-entry workload at the front of the funnel, where the highest volume of repetitive work currently sits.

The current process

An RFP arrives by email with up to thirty attachments covering census, plan of benefits, claims history, contracts, and network listings. Data is manually converted, normalized, and re-keyed into Fusion to create the submission. Volume is high, formats vary by producer, and every record carries protected health information.

What Phase 1 delivers

Email arrives, is classified as an RFP, attachments are categorized, structured fields are extracted, and the census is normalized to the Excess Reinsurance schema. Output is either uploaded directly to Fusion through a confirmed integration path, or delivered as a single standardized file ready for one-click upload by an underwriter.

What stays in place

Fusion remains the system of record. The existing work-stream routing logic, the underwriter assignment by carrier and state, and the case status pipeline from nascent through quoted to sold are all preserved. Underwriters and salespeople work the same Fusion experience they do today.

Plus 1 recommendation

Begin with Option 1 · Microsoft Stack

Three architectures are presented in the next tab. Plus 1 recommends Option 1, a Microsoft-native build using Power Automate, Copilot Studio agents, and Azure Functions for any code-driven extraction. The recommendation is conditional on AON confirming Azure OpenAI availability under the existing enterprise BAA and on the Fusion software team confirming the integration surface. If either condition cannot be met, Option 2 or Option 3 provides a clear fallback path.

Why Option 1 first

Stays inside the AON Microsoft tenant, leverages tooling already approved by AON IT, requires no new vendor onboarding for security review, and delivers the fastest path to a working pilot. The build draws on Power Automate for orchestration, Copilot Studio agents for classification and extraction, and Azure Functions where deterministic code is the right tool for handling protected fields.

Future engagements (separately scoped)

Two adjacent opportunities surfaced during discovery and remain available for a future phase. The first applies AI summarization to long-form case management documentation as decision support for underwriters. The second is an advisory engagement on broader process re-engineering. Both will be scoped after Phase 1 is deployed and stable.

Three paths · same outcome

Three architectures, sequenced by Plus 1 preference

Each option ships the same Phase 1 outcome. The differences sit in where the workflow runs, who owns the BAA, and how protected information moves through the system. Option 1 is recommended subject to two confirmation conversations during the discovery sprint. Option 3 is positioned as a fallback that combines the strengths of Options 1 and 2 if Microsoft agents alone cannot achieve the extraction accuracy required.

8–14 hrs
Estimated
Census columns vary across producers. The mapping to the Excess Reinsurance standard schema (age, sex, dependents, ZIP and region) is decided once per producer with AI assistance and then locked. From that point on, every census from that producer is transformed deterministically by code, with no protected information sent to an LLM. The mapping is reviewed only when a producer changes its source format.
