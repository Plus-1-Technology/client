04 — The Decision

Why We Transitioned to Azure

Once the n8n pilot confirmed the extraction logic worked, we had a decision: follow the original path through .NET, or move directly to Azure. We chose Azure, and here's why.

The .NET step became unnecessary

The original reason for a .NET migration was to get the proven pipeline into the PhaseAlpha application stack. Azure Container Apps gives us a production-grade, managed runtime without rewriting the service in a different language. Adding a .NET port on top of a working service would have added 120–200 hours with no functional benefit.

Everything under one roof

The pilot stack had components across three platforms: n8n for orchestration, Railway for hosting, and third-party APIs for parsing and AI. That means three vendor relationships, three billing accounts, and three places for something to go wrong. The Azure build puts all of it into one environment that already fits inside PhaseAlpha's Microsoft ecosystem.

Security and ownership

The pilot used API keys across multiple services. The current setup uses Azure Key Vault and Managed Identity — no credentials in code, and access controlled at the resource level. When the service moves to your Azure tenant, you own it outright with no ongoing dependency on Plus 1 infrastructure.

Cost

The original proposal estimated $0.054–$0.91 per schedule page depending on the approach. The Azure-native build is running at roughly $0.02 per job in current testing. That reduction comes from removing LlamaParse (a paid third-party tier) and consolidating AI review into a single Azure OpenAI call instead of multiple passes.
